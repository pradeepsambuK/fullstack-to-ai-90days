01 — Overview

What this app is

Finance Copilot answers questions about your bills and spending — due dates, category totals, subscriptions, overdue items — without hallucinating balances. It does that with Retrieval-Augmented Generation (RAG): facts live in documents, the model only phrases the answer.

Why RAG instead of fine-tuning? Bills change weekly. Fine-tuning bakes in stale facts and costs a training run per update. RAG updates the moment a new bill is indexed — delete a chunk and the fact is gone.

02 — Pipeline

The RAG pipeline, end to end

Ingest→Chunk→Embed→Store→Retrieve→Generate→Cite

Ingest: bills (manual, PDF, or Plaid sync), transactions (CSV / bank feed), and pasted statements are normalised to plain text with metadata: amount, date, category, source.

At question time the query is embedded, the top-k most similar chunks are fetched, and only those chunks are placed in the model’s context window with an instruction to answer from them alone and cite chunk IDs.

03 — Chunking

Chunking strategy

One bill = one chunk (it’s already atomic). Long statements are split on line breaks first, then windowed:

function chunkText(text, size = 280, overlap = 40) {
  const chunks = [];
  for (let i = 0; i < text.length; i += size - overlap) {
    chunks.push(text.slice(i, i + size));
  }
  return chunks; // each keeps { docId, amount, date, category }
}

Overlap prevents a total that straddles a boundary from being lost. Metadata travels with every chunk so retrieval can filter by date or category before ranking by similarity.

04 — Embeddings

Embeddings: text → numbers that mean meaning

An embedding model maps each chunk to a dense vector (e.g. 1536 floats). “Electric bill due Friday” and “power payment deadline” land close together in vector space even with no shared words — that’s what keyword search can’t do.

const { embedding } = await embed({
  model: 'text-embedding-3-small',
  input: chunk.text
});
// store embedding alongside chunk.text + metadata

This demo: runs transparent keyword/TF scoring in-browser so you can audit every score. Swap that one function for cosine similarity over real embeddings and the rest of the app is unchanged — that seam is deliberate.

06 — Retrieval

Retrieval & ranking

Retrieve top-k = 4–6, then re-check with hard filters: a “due this week” question also filters due_date to the next 7 days, so a semantically-similar bill from last month can’t pollute the answer. Totals (subscriptions, groceries) are computed deterministically from the retrieved rows — the LLM never does arithmetic on faith.

07 — Generation

Grounded generation & citations

System: Answer ONLY from the chunks below.
If the chunks don't contain the answer, say so.
Cite every figure like [chunk_12].

Chunks:
[chunk_12] Electric — $142.10 — due in 2 days…

That single constraint — plus showing the chunks in the UI, as this demo does under every answer — is what makes the output auditable. If a number has no citation, it doesn’t ship.

08 — Cloud

Cloud architecture

Netlify / Vercel — static UI→Serverless API (Edge Fn)→Supabase — Postgres + pgvector + Auth→Embedding + LLM API

Frontend: static, CDN-cached, zero servers to patch. API: one serverless function (/api/ask) that embeds the query, runs the pgvector search, and calls the LLM — keys stay server-side, never in the browser. Ingest: a scheduled function (or Plaid webhook) adds new transactions nightly. Scaling: every layer is pay-per-use; the free tiers comfortably cover a personal deployment.

09 — Data & security

Data model & security

TableKey fields
billsid, user_id, name, amount, due_date, category, status
transactionsid, user_id, merchant, amount, date, category
chunksid, source_id, text, embedding vector(1536), metadata jsonb

Row-Level Security on every table (user_id = auth.uid()), bank tokens held only by the aggregator (Plaid) — never stored raw — and this public demo ships with fictional data and stores nothing at all.

10 — Production

Going to production — checklist

  • Replace demo keyword scoring with real embeddings + pgvector (Section 5 query).
  • Move /api/ask behind auth; add per-user rate limits.
  • Connect Plaid (or CSV import) for automatic transaction ingest.
  • Add evals: 30 golden questions with known answers, run on every deploy.
  • Log retrieved chunk IDs with every answer for audit.
